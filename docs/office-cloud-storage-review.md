## How cloud copies work

The client sends small upload metadata to the Edge Function: a real Office workspace ID, filename, MIME, byte length, SHA-256 and idempotency key. The Function verifies COCCE Auth and derives the actor; the client cannot supply it. Service-role-only Office RPCs independently check active membership and ownership/roles.

Quota reservation is serialized by the workspace quota row. The server creates keys only under `office/v1/workspaces/<workspace>/files/<file>/revisions/<revision>/payload`. A five-minute-or-shorter signed PUT fixes size, MIME, checksum and session headers; the browser transfers directly to Bunny. File bytes never pass through Vercel or the Edge Function. Finalization uses metadata-only HEAD checks; only verified revisions become listable.

Downloads recheck membership and use file-specific, two-minute links with generic `application/octet-stream` attachment responses. This is not a public CDN or inline preview. The browser adapter validates the fixed host/path/workspace/file, bounds downloaded bytes, verifies SHA-256 and sends no JWT/public key/cookies to Bunny. Signed URLs are not persisted.

## Bounded Docs cloud copies

The new panel reuses existing Office sign-in and lists actual active server workspaces; browser-local workspace IDs are never authorization. No document content is sent on opening the panel, signing in, selecting a workspace or viewing usage/listing. Upload requires an affirmative confirmation identifying the full document text/formatting, Frankfurt storage, workspace-member access and the preservation of the local original. This does not authorize AI processing.

The copy envelope contains only a format/version marker, title and supported sanitized HTML. It excludes local IDs, timestamps, history, authentication and AI metadata. Limits are 3 MiB for the envelope, 2 MiB markup, 200,000 Unicode text characters, 10,000 blocks and a 200-character title. Unsupported/lossy markup is refused rather than silently stripped. Existing supported simple tables round-trip; complex tables remain refused. Drafts with any review comments or unreadable comment storage are refused before confirmation/upload, because this first format cannot preserve that sidecar.

A bounded local journal stores account/workspace/opaque document IDs, safe filename, size/hash, idempotency key and returned recovery IDs/deadline. It stores no document body, signed URL or credential. Journal write failure prevents reservation/transfer. Uncertain transfers retain recovery records; checks do not re-upload content. Account/workspace changes and unmount abort transfers and suppress stale results.

Restore is explicit, size/checksum/schema validated and saved as **one new local document**. It does not replace any existing ID or draft. One atomic local save must succeed before selection changes; save failure preserves existing storage. Cloud trash/restore is explicit, recoverable and separate from local documents. Trash still counts toward quota. A read-only meter shows server tier, active/trash/pending bytes, total/available bytes and 80/90/100 warnings. This is not live sync, shared editing, version merging, a complete backup format or an administrator quota editor.

## New recovery lookup — deployed and synthetically verified

Review found a real gap before enabling the UI: if the first reservation response is lost, its session ID is unknown locally. Retrying `begin_upload` after expiry fails inside the existing SQL RPC (`55000`), so a client cannot discover that ID. Re-entering begin can also create a fresh reservation if the original never committed. The new UI must not rely on that behavior.

The exact owner-approved migration `supabase/migrations/20261104112200_office_cloud_upload_lookup.sql` (SHA-256 `88eb027ae2f080828dd5ba0a01f60fd44fc389c3eea9b54929ea3352be52f45e`) was applied through the supported Supabase migration interface and recorded as version `20261104113618 / office_cloud_upload_lookup`. A live catalog check confirmed the intended signature, `SECURITY DEFINER`, empty search path, `service_role` execute, and no execute for `authenticated` or `anon`. It adds only `office_cloud_find_upload(actor, workspace, idempotency)`. It checks active membership before lookup, searches only the actor's matching session, then reuses `office_cloud_get_upload`. It creates no table and performs no row, quota, audit, wallet or shared-setting writes.

The deployed Function v3 adds only an exact-key `resolve_upload` action and the RPC allowlist entry. It derives the actor from Auth, validates the returned creator/workspace, and returns safe IDs/status/deadline and a bounded session-state discriminator—not a URL, object path, checksum or credential. Active/expired/failed sessions can be discovered without renewing or signing them. A definitive authorized no-record result is `404 UPLOAD_LOOKUP_NOT_FOUND`; access denial remains 403. The client clears an unstarted journal only for that exact allowlisted code, never for a generic gateway 404. Failed non-final sessions wait through their existing expiry before recovery; they are not sent to finalization. Each check re-reads current state, even when the ID is already journaled. Existing upload/finalize/recovery behavior and grace policy remain unchanged.

## Quotas, recovery and deletion limits

Product defaults are decimal allowances, independent of Bunny capacity: Personal 5 GB, Small Office 25 GB, SME 100 GB, School/College 250 GB, Enterprise 1 TB and Government/Large Institution 2 TB. A new workspace currently defaults to Small Office. The per-file transport cap is 25 MiB, distinct from workspace capacity and the smaller Docs envelope cap. A workspace is counted as verified active bytes + verified trash bytes + unreleased reservations. Writers use the quota row first; concurrent reservations cannot exceed it. The browser accepts large aggregate quotas and an over-quota readout with zero available bytes; it does not hide/delete existing files.

Sessions expire after 15 minutes. A completed object awaiting registration is recovered, not deleted. Absence requires a fresh 404 after the first-observed 24-hour grace before releasing reservations; provider/network errors do not release them. This reduces but does not prove away slow in-flight PUT risk. The current path uses single PUTs only; it does not create multipart parts. Multipart, a scheduled reaper, automatic reconciliation, physical deletion, retention/legal hold and provider-side versioning are not implemented or claimed.

The internal service-role tier RPC permits downgrades only when usage fits and refuses increases. No free-upgrade endpoint exists. Administrator quota configuration/dashboard, personal-file workspace provisioning, multi-zone routing, all-editor bundles/media/sidecars, two-account/cross-device tests and load testing remain pending.

## Coins and wallet remain blocked

The uploaded brief proposes one-time packages (+5 GB/2,000 Coins; +25 GB/7,500; +100 GB/20,000; +250 GB/40,000; +1 TB/100,000; +5 TB/350,000; 1 Coin = 1 TZS). They are proposals, not approved prices or code constants. No purchase test or debit occurred.

Existing `wallet_atomic_vip` and `wallet_atomic_boost` are product-specific, lack a storage entitlement operation and do not provide server PIN validation for this path. Client-side PIN comparison/separate profile and ledger writes are not an acceptable template. Storage purchases need a separately reviewed Office-only atomic operation that validates the PIN server-side, uses the canonical locked wallet balance and grants quota in the same transaction. Do not alter shared wallet objects, reuse unrelated product purchases, invent prices or write balances/ledgers directly.
